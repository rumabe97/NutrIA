# Carousel

A horizontally scrolling carousel built on native CSS scroll-snap. Touch swipe, momentum, and arrow-key navigation all work natively; React orchestrates programmatic navigation, indicator state, and accessibility wiring on top.

The DS implementation is intentionally **minimal** compared to libraries like Embla — no looping, no autoplay, no plugins, no axis switching. Most product carousels (image galleries, featured items, testimonials, onboarding flows) only need the core "horizontal swipe + prev/next + dots" pattern, and modern browsers give us most of that for free.

## Anatomy

```tsx
<Carousel aria-label="Featured products" roleDescription="carousel">
  <CarouselViewport>
    <CarouselItem roleDescription="slide">…</CarouselItem>
    <CarouselItem roleDescription="slide">…</CarouselItem>
    <CarouselItem roleDescription="slide">…</CarouselItem>
  </CarouselViewport>
  <CarouselPrevious aria-label="Previous slide" />
  <CarouselNext aria-label="Next slide" />
  <CarouselIndicators getIndicatorLabel={(i, total) => `Go to slide ${i + 1} of ${total}`} />
</Carousel>
```

- **`Carousel`** — root region with shared state via context. Requires `aria-label` or `aria-labelledby` (TS-enforced)
- **`CarouselViewport`** — the scrollable container with CSS scroll-snap. Tracks the active slide via `IntersectionObserver`. Keyboard-focusable; arrow keys / Home / End navigate
- **`CarouselItem`** — a single slide. Defaults to 100% width of the viewport; override with `className` for multi-slide layouts
- **`CarouselPrevious` / `CarouselNext`** — chevron buttons that scroll to the adjacent slide. Auto-disable at the edges
- **`CarouselIndicators`** — dots showing position. Uses a roving tabindex — single tab stop, arrow keys move between dots

### Drag free

Set `dragFree` to disable scroll-snap. Swipes/scrolls land wherever momentum carries them — slides don't lock to position. `Previous` / `Next` and indicators still snap programmatically to specific slides.

**Where it shines:** image galleries, "browse-a-row" layouts (Netflix-style), product carousels where exact alignment is less important than smooth continuous browsing.

**How it interacts with each input:**

- **Touch** — native scroll + momentum + rubber-band. No velocity-based snap override (the whole point is free scrolling).
- **Trackpad** — native horizontal scroll, lands freely.
- **Mouse wheel / scrollbar** — native, free.
- **Mouse pointer-drag** — not provided. Mouse users navigate via the Previous / Next buttons or the indicators, which still snap to specific slides.

### Thumbnails (using `useCarousel`)

For more elaborate navigation than dots — a row of labelled thumbnails, a vertical list, a progress bar — read the carousel state via the `useCarousel` hook and render whatever you want. The example below builds a thumbnail row from the same data used for slides; clicking a thumbnail jumps to that slide, and the active thumbnail highlights as you scroll.

<Preview code={`import {
  Carousel,
  CarouselViewport,
  CarouselItem,
  CarouselPrevious,
  CarouselNext,
  useCarousel
} from 'ui/components/Carousel';

const items = ['Mountains', 'Ocean', 'Forest', 'Desert'];

Accepts all standard `<div>` HTML attributes (`className`, `style`, `id`, etc.).

### `CarouselViewport`

Accepts all standard `<div>` HTML attributes (except `dir`, which is reserved). The viewport is the scrollable element; pass `className` to override width, height, padding, or `gap`.

### `CarouselItem`

Accepts all standard `<div>` HTML attributes. Defaults to 100% viewport width (one-slide-per-page). Override the width via `className` (or `style`) for multi-slide layouts.

### `CarouselPrevious` / `CarouselNext`

Accepts all standard `<button>` HTML attributes. The default `aria-label` is "Previous slide" / "Next slide"; override via `aria-label` for localization. Auto-disables when there's no adjacent slide to scroll to.

### `CarouselIndicators`

Accepts all standard `<div>` HTML attributes (except `dir`). Renders nothing when `slideCount <= 1` to avoid a single useless dot. Uses a roving tabindex internally — keyboard users get a single tab stop and arrow-key navigation between dots.

## Hook — `useCarousel`

For custom UI that needs to read or control the carousel from outside the standard parts:

function SlideCounter() {
  const { currentIndex, slideCount } = useCarousel();
  return (
    <small>
      Slide {currentIndex + 1} of {slideCount}
    </small>
  );
}

## Accessibility

- **Root has `role="region"` + `aria-roledescription="carousel"`.** Combined with the required `aria-label` (or `aria-labelledby`), it becomes a named landmark for screen-reader navigation.
- **Each `CarouselItem` has `role="group"` + `aria-roledescription="slide"`.** Screen readers announce each as a slide, not just a generic `<div>`.
- **Keyboard navigation** lives on `CarouselViewport`. Focus the viewport, then:
  - `ArrowLeft` / `ArrowRight` — previous / next slide (or page, with `slidesToScroll`)
  - `Home` / `End` — first / last slide
  - The viewport's `:focus-visible` style shows the active focus ring
- **Buttons auto-disable** at the boundary slides so screen readers announce "Previous slide, dimmed" rather than letting users uselessly activate a no-op.
- **Indicators use a roving tabindex** (`RovingFocusGroup`) — single tab stop on the active dot, `ArrowLeft`/`ArrowRight` to move between dots, `Enter`/`Space` to activate. This avoids the 10+ tab stops of "one dot = one tab stop" and matches the WAI-ARIA Authoring Practices for carousel pagination.
- **Touch behaviour** is hybrid. Native CSS scroll-snap handles 1:1 finger tracking, momentum, and rubber-band overscroll. On top of that, a touchend listener measures the swipe **velocity** — if the gesture exceeds a "deliberate flick" threshold (`0.3 px/ms` over `≥ 20 px` of horizontal travel), `scrollNext` / `scrollPrev` runs and overrides the native position-based snap. The combination matches the iOS UIScrollView paging feel: slow drags settle by distance, quick flicks always advance.
- **Respects `prefers-reduced-motion`.** Button / indicator / keyboard navigation defaults to a smooth scroll, but the component reads `matchMedia('(prefers-reduced-motion: reduce)')` on every `scrollToIndex` call and falls back to an instant jump when the user has opted out of motion. This handles the WHATWG CSSOM View footgun where `Element.scrollTo({ behavior: 'smooth' })` from JS overrides the CSS `scroll-behavior: auto !important` set by [`ui/styles/base.css`](../../../../packages/ui/src/styles/base.css)'s reduced-motion baseline.

## What's intentionally not here

This carousel deliberately omits features that bloat most production carousels but rarely earn their weight:

- **Looping / infinite scroll** — adds significant complexity and breaks scroll-snap. If you genuinely need looping, the right move is to switch to a JS-driven engine (Embla, Swiper) for that specific feature.
- **Autoplay** — accessibility hostility (people with cognitive disabilities lose track) and usually not what users actually want. If a project needs it, add it as a wrapper component, not in the DS.
- **Vertical orientation** — the API would diverge enough (CSS, keyboard handlers) that a `Carousel` and a `VerticalCarousel` should be separate primitives. Add the second one if and when there's a real need.
- **Pointer-drag-by-mouse on desktop** — touch carousels are common and worth investing in; desktop pointer-drag is a less expected interaction (most users reach for the prev/next buttons or trackpad-swipe). Skipping it keeps the implementation small. `dragFree` consequently means "no snap" — on desktop it relies on trackpad/wheel; mouse users navigate via buttons.
- **Plugin system** — engineering for a feature surface area we don't have.

These omissions are deliberate. The carousel that ships with the DS is the carousel that most apps actually need.
