# Text

A typographic primitive for any non-heading text — paragraphs, captions, labels, small print. Defaults to a `<p>` with body size, regular weight, and primary tone.

Use `Text` instead of raw `<p>` / `<span>` whenever the styling is intentional (which is most of the time in an app). It centralizes the vocabulary — `size`, `weight`, `tone`, `align` — so every paragraph in the app draws from the same scale.

### Tones

`tone` maps to the foreground tokens. Use `secondary` for de-emphasized content, `disabled` for unavailable text.

`tertiary` is intentionally sub-AA (it maps to `--foreground-03`, designed for **decorative non-text** like placeholders and dots). Use it sparingly for content where slight contrast trade-off is acceptable — non-essential metadata, watermark-style captions. For genuine body text — including hints, helper text, and important metadata — reach for `secondary` instead.

<Preview code={`import { Text } from 'ui/components/Text';

export default function Example() {
  return (
    <>
      <Text>Primary — full-emphasis body text</Text>
      <Text tone="secondary">Secondary — slightly muted, for supporting copy</Text>
      <Text tone="tertiary">Tertiary — strongly muted, for hints and metadata</Text>
      <Text tone="disabled">Disabled — for unavailable text</Text>
    </>
  );
}`}>
  <Text>Primary — full-emphasis body text</Text>
  <Text tone="secondary">Secondary — slightly muted, for supporting copy</Text>
  <Text tone="tertiary">Tertiary — strongly muted, for hints and metadata</Text>
  <Text tone="disabled">Disabled — for unavailable text</Text>
</Preview>

### Semantic inline tags

Use the semantic HTML element that matches the **meaning** of the text. The browser's user-agent stylesheet applies the right visual default automatically (bold for `<strong>`, italic for `<em>`, line-through for `<s>`, yellow background for `<mark>`).

<Preview code={`import { Text } from 'ui/components/Text';

export default function Example() {
  return (
    <>
      <Text>
        Make sure you <Text as="strong">save your work</Text> before closing the tab.
      </Text>
      <Text>
        This is <Text as="em">strongly recommended</Text> for new accounts.
      </Text>
      <Text>
        <Text as="s">Old price $50</Text> — now $29.
      </Text>
      <Text>
        Recent change: <Text as="mark">the API endpoint moved</Text> last week.
      </Text>
    </>
  );
}`}>
  <Text>Make sure you <Text as="strong">save your work</Text> before closing the tab.</Text>
  <Text>This is <Text as="em">strongly recommended</Text> for new accounts.</Text>
  <Text><Text as="s">Old price $50</Text> — now $29.</Text>
  <Text>Recent change: <Text as="mark">the API endpoint moved</Text> last week.</Text>
</Preview>

> `<Text as="strong">` renders bold because of the browser default — Text only applies the `weight` class when you pass the prop explicitly. If you want strong-but-not-bold, pass `weight="regular"`. If you want bold without the semantics, use `<Text weight="bold">`.

## When NOT to use Text

- **For headings** — use `Heading`, not `<Text size="lg" weight="semibold">`. The semantic tag matters.
- **For inline code** — use `Code`.
- **For purely decorative or one-off styling** — write the CSS in your component's module. Text is for the recurring vocabulary, not for every styled span.

## Extending `tone` for semantic states

`tone` currently covers emphasis tiers (primary / secondary / tertiary / disabled). Some projects also need semantic states — success, warning, error — to colour inline messages like "Saved" or "Invalid email." The DS already defines `--color-success`, `--color-warning`, `--color-error` tokens, so the extension is small and mechanical:

```ts
// Text.tsx — widen the type
type TextTone = 'primary' | 'secondary' | 'tertiary' | 'disabled' | 'success' | 'warning' | 'error';
```

```css
/* Text.module.css — add the matching classes */
.tone-success { color: var(--color-success); }
.tone-warning { color: var(--color-warning); }
.tone-error { color: var(--color-error); }
```

That's the whole change. The same pattern applies to `Heading` if you ever need semantically-coloured headings (rare).

**Naming convention:** keep the state names matching the existing token suffix (`--color-success` ↔ `tone="success"`). Don't invent new names ("ok", "danger", "alert") — symmetry with the token catalog is what makes the API memorable.

**When NOT to extend:** if the colour is only used in *one* component (e.g. a per-field error message in `Input`), don't put it in `tone` — Input already uses `--color-error` directly via its own `.invalid` CSS class. `tone` is for colours that need to be settable from JSX across many components.

## Accessibility

Defaults to `<p>` and respects the semantic tag you pass via `as` — that's the whole accessibility story.

- **Choose `as` semantically.** `<p>` for paragraphs, `<span>` for inline runs, `<strong>` / `<em>` / `<mark>` / `<s>` when the emphasis is meaningful (assistive tech announces them). Use `as="span"` for inline copy — don't nest a `<p>` inside another `<p>`.
- **`tone` is not a substitute for semantics.** Coloured text alone doesn't convey state to screen readers or to colour-blind users. For a real error/success message, pair the visible Text with an `aria-live` region or a leading icon with a label.
- **Don't strip text into images.** Keep the words in the DOM so they're selectable, translatable, and zoomable.
