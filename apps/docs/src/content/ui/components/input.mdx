# Input

A text input with a built-in, required label, optional hint text, and optional error message. The label is enforced via TypeScript — you cannot render an `Input` without one. The hint and error are linked to the input via `aria-describedby`, so screen readers announce them when the input is focused.

Built on the native `<input>` element with `<label htmlFor>` linkage. Generates a stable id automatically (via `useId`) and reuses it for the hint and error ids.

All standard `<input>` HTML attributes are also accepted (`value`, `defaultValue`, `onChange`, `placeholder`, `name`, `min`, `max`, `pattern`, etc.). The `id` prop is intentionally omitted — `Input` generates its own stable id.

## Use in forms

Input is designed for the React 19 + Next.js server-action form pattern. The `error` prop is the integration point — pass the per-field error string from the action's returned state:

```tsx
'use client';
import { useActionState } from 'react';
import { Input } from 'ui/components/Input';
import { Button } from 'ui/components/Button';
import { registerAction } from './_actions/register';

export function RegisterForm() {
  const [state, action, isPending] = useActionState(registerAction, { errors: {} });

  return (
    <form>
      <Input
        defaultValue={state.email}
        error={state.errors?.email}
        label="Email"
        name="email"
        required
        type="email"
      />
      <Input
        error={state.errors?.password}
        label="Password"
        name="password"
        required
        type="password"
      />
      <Button formAction={action} type="submit" disabled={isPending}>
        {isPending ? 'Submitting…' : 'Register'}
      </Button>
    </form>
  );
}
```

The full pattern is documented in `apps/web/AGENTS.md` under "Forms".

## Accessibility

- The `label` prop is required at the type level — no Input can be rendered without an accessible name.
- `<label htmlFor={id}>` is linked to `<input id={id}>` so clicking the label focuses the input and screen readers announce the label.
- When `hint` is set, the input gets `aria-describedby` pointing at the hint paragraph — screen readers announce the hint when the input is focused.
- When `error` is set, the input gets `aria-invalid="true"` and `aria-describedby` pointing at the error paragraph. The hint is hidden so the error takes its place.
- The error paragraph is `aria-live="polite"` — screen readers announce the message when it appears, not just when the input is re-focused. This is the [common DS pattern](https://primer.style/) (Primer, Carbon) and works without interrupting whatever the screen reader is currently reading.

### Validation timing — prefer on-blur or on-submit

Because the error is in a live region, setting it on **every keystroke** causes the screen reader to announce on every change — chatty and disorientating. Validate when the user has paused or moved on:

- **`onBlur`** — validate when focus leaves the field. Good for "is this email valid?" checks.
- **`onSubmit`** — validate when the form is submitted (the React 19 server-action pattern shown above does this automatically). Good for "do these passwords match?" / "is this username taken?" checks.

If you genuinely need live validation as the user types (e.g. a password-strength indicator), **debounce** the error state in your form layer (~300ms) before passing it to the Input.
- Generated ids use React's `useId()`, stable across SSR and client hydration.
