# packages/database AGENTS.md

Database client, schema definitions, and migrations. Rules here are more specific than root `AGENTS.md` — both apply.

---

## What lives here

```
src/
  client.ts          — the database() factory and ping()
  env.ts             — required() — fails loudly on a missing connection string
  schemas/           — one .schema.ts file per table, plus _columns.ts / _enums.ts / _utils.ts
  migrations/        — generated by drizzle-kit, never edit by hand
  seed/              — reference data: the allergen catalogue and the ingredient set
drizzle.config.ts    — drizzle-kit config (migration generation + push)
```

## The `database()` factory

`src/client.ts` exports a single `database()` function returning one lazily-created Drizzle
instance. Call it at the top of every repository method; do not hold the result across
requests.

```ts
import { database } from 'database';

await database().select().from(profiles).where(eq(profiles.userId, userId));
```

There is **one** client, not an admin/RLS pair. `apps/api` is the only process that opens a
connection, so there is no untrusted caller for a database policy to constrain —
**authorisation is the `WHERE userId = …` in `packages/core/repositories`, and a query
missing it is a data leak.** See
[`docs/decisions/0002`](../../docs/decisions/0002-drizzle-on-neon.md).

`ping()` runs `SELECT 1` for the API's readiness probe. Keep SQL construction in this
package: `drizzle-orm`'s types differ between its ESM and CommonJS resolutions, so a `sql`
tag built in `apps/api` (ESM) does not satisfy a signature from here (CommonJS).

### Connection strings

- `DATABASE_URL` — the **pooled** Neon endpoint (host contains `-pooler`), used at runtime.
  The client sets `prepare: false` because the pooler is PgBouncer in transaction mode and
  cannot carry named prepared statements across checkouts.
- `DIRECT_DATABASE_URL` — the **direct**, session-mode endpoint. `drizzle.config.ts` only.
  DDL cannot run through the pooler.

## This package compiles

`exports` resolves `types` to source and `default` to `./dist` (CommonJS), because
`apps/api` is a Node process, not a bundler. **Run `pnpm --filter database build` after
changing anything here**, or leave `pnpm dev` running, which watches.

## Schemas

Each table has its own file: `src/schemas/<table>.schema.ts`. Export the table as a named const matching the table name.

```ts
// src/schemas/users.schema.ts
export const users = pgTable('users', {
  id: uuid().primaryKey().defaultRandom(),
  name: text().notNull(),
  email: text().notNull().unique(),
  createdAt: timestamp({ withTimezone: true }).notNull().defaultNow()
});
```

**Naming conventions:**

- Table names: plural snake_case (`users`, `user_profiles`)
- Column keys in the schema: camelCase (`createdAt`, `userId`)
- Drizzle is configured with `casing: 'snake_case'` — it maps camelCase keys to snake_case SQL columns automatically. This means `userSchema.parse(row)` works directly without manual field mapping.

**One row per user?** Use `userOwnedSingleton()`, not `userOwned()`. It puts a UNIQUE
constraint on `userId` rather than a plain index, and that is what `ON CONFLICT (user_id)`
matches against — an upsert against a merely-indexed column fails at runtime with Postgres
42P10, which reaches the user as an opaque 500. `profiles`, `user_preferences` and
`onboarding_state` are the singletons today. `src/schemas/schema.test.ts` enforces this.

**User-owned tables (one-to-many):** use the `userOwned()` helper from `_utils.ts`. It gives the table an
`id`, a `userId` foreign key with `ON DELETE CASCADE`, timestamps, and — the part that is
easy to forget — an index on `userId`, which every ownership-scoped query filters on. The
cascade is what makes account deletion actually delete a person's data; it is not a
convenience.

**Enums** live in `_enums.ts`, shared column groups in `_columns.ts`. `_columns.ts` exists
separately from `_utils.ts` because `userOwned()` needs the `user` table while
`auth.schema.ts` needs the timestamp columns — putting both in one module is a cycle that
drizzle-kit hits at config load.

**Snapshot what history must preserve.** `meals` stores its own kcal and macros rather than
recomputing from the recipe, so a completed plan keeps showing what the user actually ate
after a recipe is later corrected.

## Migrations

Migrations are generated by drizzle-kit — **never edit migration files by hand**.

```bash
# Generate a migration after changing a schema
pnpm generate

# Apply migrations to the database
pnpm migrate

# Push schema directly (dev only — skips migration files)
pnpm push
```

## Adding a new table

1. Create `src/schemas/<table>.schema.ts` and export the table const.
2. Run `pnpm generate` to create the migration.
3. Run `pnpm migrate` (or `pnpm push` in dev) to apply it.
4. Import the table in the relevant repository inside `packages/core`.

The schema file is imported by `packages/core` repositories via `'database/schema/<table>'` — the export path is defined in `package.json`.

## What does NOT belong here

- Repository logic (lives in `packages/core/src/repositories/`)
- Business rules (lives in `packages/core/src/controllers/`)
- Application code of any kind

This package's only job is to provide the database connection and the table definitions.
